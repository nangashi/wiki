# insight設計品質基準

**design_rubric_version: 1**

設計の作成と独立レビューで共有する正本。[設計schema](../design-schema.md)は形式、[評価プロトコル](evaluation-protocol.md)は実行方法を定める。実質改定では設計versionを上げる。記事基準versionとは独立に管理する。

[再利用性基準](reusability-criteria.md)のR1〜R4を適用する。R1・R2、および異領域一般化を採用理由にする場合のR3を満たさない設計は不合格。R4の欠落は利用判断を変える場合に必須対応とする。ゲートに合格した設計は以下の五観点を十分／要対応で評価する。不合格時は対象外とする。

| 観点 | 作成・レビューの条件 |
|---|---|
| 読者・目的 | 読者の状況と使い道が具体的で、概念を覚えるだけでなく未知ケースの理解・判断へ進める |
| 読後の到達点 | 読者が説明・見分け・判断できることが明示され、本文から達成を確認できる。到達点自体が不足・過剰でない |
| 内容と順序 | 内容に役割があり到達点へつながる。説明の前提がそろい、研究結果の列挙が理解の入口にならない |
| 主張と根拠・境界 | 主要主張を資料へ追え、観察・解釈・記事側の提案、条件・比較・時点・効果の強さが分かる。必要な調査を解消している |
| 採用・省略 | 比較・現実の理解・行動指針の採否が目的に照らして妥当。定義に不要という理由だけで有用な内容を落とさず、網羅や形式的な対策の追加もしない |

比較を採るなら、相手と共通の比較軸、見分ける意義を決める。現実への適用なら、どの状況の見方がどう変わるかを決める。行動指針なら、いつ何をするか、実証された効果と概念からの提案を区別する。三つの節を全記事に強制しないが、各採否と理由は残す。

見出し・段落数・字数を合否条件にしない。執筆担当が内容の採否を考え直さず本文を書ける具体性が必要であり、短い目次だけでは足りない。逆に設計を本文の下書き全文にしない。

レビュー担当は設計者の目的設定も検証する。設計内で整合していても、重要な混同や現実の利用判断を扱えないなら指摘する。根拠不明は誤りと断定せず、採否や説明・利用判断を変える未確認主張だけ調査必須とする。

対応項目は修正必須／調査必須／任意改善に分け、具体的な対象、読者への影響、改善後の条件を示す。要対応には必須項目を対応させる。一つの問題を複数観点へ重複計上しない。任意改善は執筆開始を妨げず、必須項目が解消するまで独立再評価する。統括は評価の判定を代行しない。
