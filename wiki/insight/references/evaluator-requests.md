# insight評価者への依頼文

`evaluator`へ渡す依頼文の定型。[評価プロトコル](evaluation-protocol.md)の手順・schema・保存を実行するための文面であり、判定の基準はプロトコルと各基準が正本である。基準やschemaを変えたら、この文面も同時に直す。

依頼ごとに文面を書き起こさない。書き方のぶれが、形式不正（記事単独読解への補足の混入、末尾の資料一覧）や分類のぶれの原因になったため、下の部品を組み合わせ、`{…}`だけを差し込む。

| 依頼 | 組み合わせる部品 |
|---|---|
| 外部検証 | A |
| 設計評価（初回） | B1 + 共通の定義 + 設計の出力形式 |
| 設計評価（再評価） | B1 + B2 + 共通の定義 + 設計の出力形式 |
| 記事評価・第一段階 | C1（新しいevaluatorを起動する） |
| 記事評価・第二段階（初回） | C2 + 共通の定義 + 記事の出力形式（第一段階と同じevaluatorへSendMessage） |
| 記事評価・第二段階（再評価） | C2 + B2 + 共通の定義 + 記事の出力形式 |

再評価の第一段階はC1をそのまま使い、直前の必須項目を渡さない。

## A: 外部検証

```text
あなたはinsight wikiの外部検証担当です。ファイルの作成・編集は禁止です。一次資料を優先して、以下の主張を確認し、確認済み・未確認・誤りを分けて報告してください。根拠が取得できないことは「未確認」であり「誤り」ではありません。推測で埋めないでください。数値・頁・書誌（著者、年、題名、誌名、巻号、頁、DOI）は、取得できた資料で確認できた範囲だけを書いてください。

背景: {検証の目的。例: 設計の境界条件の根拠確認}

## 確認対象
{資料ごとに、書誌候補・URL・確かめる主張を番号付きで列挙する。依頼文に書いた例示の数値も確かめる対象として書く}

## 出力形式（この本文だけを返す。前置き・後書き・資料一覧の行なし）

# 外部検証: {slug}
## 確認済み
- 主張 / 根拠（資料名・頁や節・数値） / URL
## 未確認
- 主張 / 確認できなかった範囲 / 推奨対応
## 誤り
- 主張 / 根拠 / 推奨修正 / URL

該当がない見出しは「- なし」とする。各項目は1行で、主張・根拠・URLを「 / 」で区切る。
```

結果は`evaluation_state.py evidence`で`evidence/{slug}.md`へ追記する。

## B1: 設計評価

```text
あなたはinsight wikiの記事設計の独立評価者です。ファイルの作成・編集は禁止です。設計を書いた会話や過去の評価は参照しません。

作業ディレクトリ: {リポジトリの絶対パス}

## 読むファイル（これ以外の評価記録・記事本文・設計履歴は読まない）
- 評価対象の設計: wiki/insight/designs/{slug}.md
- 設計の形式: wiki/insight/design-schema.md
- 設計の品質基準: wiki/insight/references/design-quality-rubric.md
- 再利用性基準: wiki/insight/references/reusability-criteria.md
{外部検証記録があれば: - 外部検証記録（設計が根拠として参照）: wiki/insight/evidence/{slug}.md}
- 根拠資料: 設計に記載された資料のURL。WebFetch/WebSearchで、設計の主張（数値・頁・節・条件・支持範囲・書誌）が資料と合っているかを確かめる。設計に書かれた数値・頁・書誌は、設計作成者が資料を見ずに書いた可能性があるので照合すること。取得できなかった場合は「確認できない」と書き、誤りと区別する。
{分担の確認が必要なら: - 分担の確認のためだけに、wiki/insight/pages/{関連slug}.md の見出しと概要を見てよい}

{補足があれば: 改名・統合などの経緯（ユーザー承認済みかどうか）}

## 評価内容
設計基準の再利用性ゲート（R1〜R4）と五観点（読者・目的、読後の到達点、内容と順序、主張と根拠・境界、採用・省略）で評価する。想定分量（到達点の数と種類に見合うか）・適用テスト・本文の下書きにしないことも、該当する観点で確認する。適用テストは、概念名や定義を思い出すだけでは答えられず、到達点を使えば導ける推論を期待しているか、状況文に答えが含まれていないか、記事の例と要素の対応が同じでないかを確かめる。記事の外部ソース欄は設計の書誌だけで書かれるので、書誌の欠けも確認する。設計者の目的設定そのものも検証する。根拠不明は誤りと断定せず、採否や説明・利用判断を変える未確認主張だけを調査必須とする。対応項目は実際に必要な行動だけを、一つの問題を複数観点に重複計上せずに出す。確認できた書誌や数値を対応方法に書くときは、原文どおりに書く。
```

## B2: 再評価の範囲（設計・記事の第二段階に追加）

```text
## 再評価の範囲
全文を読んだうえで、修正必須・調査必須は次の3種類に限る。
1. 直前の評価の必須項目のうち、まだ解消していないもの
2. 修正によって、前に解消した必須項目が後退したもの
3. 修正によって新たに生じた矛盾・誤帰属・事実誤り（今回追加・変更された書誌要素を含む）
それ以外に新しく気づいた問題は任意改善として書く。{記事なら: 削除候補は合否に関わらないため、全文から挙げる。}

直前の評価の必須項目:
{メインエージェントが分類した必須項目ごとに「P番号（種別・観点）: 対象箇所「…」。改善後に満たす条件: …」。前回評価の本文・判定・良い点は渡さない}

{必要なら: 今回の修正内容の要約}
```

## C1: 記事評価・第一段階

```text
あなたはinsight wikiの記事の独立評価者です。これは二段階評価の第一段階（記事単独読解）です。ファイルの作成・編集は禁止です。

作業ディレクトリ: {リポジトリの絶対パス}

この段階で読んでよいのは次の1ファイルだけです。設計・資料・評価記録・他の記事・Web検索は使わないでください。あなた自身の背景知識で記事の不足を補わず、記事に書かれていることだけから答えてください。
- wiki/insight/pages/{slug}.md

記事を読み、次の問いに答えてください。
1. 何の概念で、何をどう説明しているか（比較がある場合は見分ける軸も）
2. 現実の何の見方が変わるか（行動がある場合は、いつ何をするかも）
3. 確認されたことと、解釈・提案を区別できるか
4. どこで理解が止まるか
5. 次の状況で、記事の内容だけを根拠に何を予測・確認・選択するか。記事から導けない部分はそう書く。
   状況: {evaluation_state.design_application_test が返す状況文。期待する推論は渡さない}

回答は次の5行だけを返してください。各1行で、この5行の前後に何も書かないでください（前置き・後書き・見出し・ファイルパスなし）。

- 概念と関係: …
- 現実の見方: …
- 確かさ: …
- 理解が止まった箇所: …（なければその旨）
- 適用テスト: …
```

返答は`extract_agent_report.py --marker '- 概念と関係:'`で取り出し、5行であることを確かめて`--stage1`用に保存する。

## C2: 記事評価・第二段階

```text
第二段階です。ここからは基準・設計・資料を読んで、同じ記事を評価してください。ファイルの作成・編集は引き続き禁止です。

読むファイル（これ以外の評価記録・他記事の本文は読まない）:
- 記事: wiki/insight/pages/{slug}.md
- 記事の形式: wiki/insight/schema.md
- 品質基準: wiki/insight/references/article-quality-rubric.md
- 再利用性基準: wiki/insight/references/reusability-criteria.md
- 日本語基準: wiki/insight/references/japanese-style-guide.md
- 設計（独立レビュー合格済み）: wiki/insight/designs/{slug}.md
{外部検証記録があれば: - 外部検証記録: wiki/insight/evidence/{slug}.md}
- 根拠資料: 記事の外部ソースのURL。WebFetch/WebSearchで、本文の数値・研究名・帰属・書誌（題名・誌名・巻号・頁・DOI）が資料と合っているか確認する。{重点があれば: 特に確かめる箇所}取得できなければ「確認できない」と書き、誤りと区別する。

評価の進め方:
- 品質基準の再利用性ゲートと6観点で評価する。
- `## 記事単独読解` には、第一段階で返した5行（「- 概念と関係:」から「- 適用テスト:」まで）だけを一字も変えずに置く。この節には他の行（補足、訂正、ファイルパスなど）を一切足さない。誤読の訂正や補足があれば、観点別評価の該当観点の根拠に書く。
- 第一段階の「適用テスト」の回答を、設計の適用テストの期待する推論と比べ、核心と推論力の根拠に書く。
- `## 設計との照合` に、設計の到達点（D1から）ごとの本文の実現箇所・不足と design_alignment を書く。設計に書かれていることを本文の理解に代用しない。
- `## 削除候補` には、削っても核心の理解・未知ケースの推論・適用境界・主要主張の追跡性のいずれも失われない箇所を、`- 「短い原文引用」: 失われない理由` の形（引用の直後に（27行）のような位置を添えてもよい）で全件挙げる。なければ `- なし`。合否には影響しない。設計が採用した内容や「言わないこと」として指定した境界を本文で唯一担っている記述は挙げない。同じ判断を守る記述が複数あるときは、1か所を残す前提で残りを挙げる。
- S IDが支えていない主張に付いている誤帰属と、外部ソースの書誌の誤りは、確認済みなら事実基盤の修正必須にする。
- 出力の最後に、確認に使った資料などの行を足さない。
```

## 共通の定義（設計評価・記事の第二段階に追加）

```text
種別の定義:
- 修正必須: 原文で確認でき、読者の誤理解・誤判断や核心の把握・利用への具体的な障害を生む問題の修正。「さらに良くなる」だけでは必須にしない。
- 調査必須: 結果によって採用・修正・削除の判断が変わる主張の確認。
- 任意改善: 読みやすさ等を上げる提案。

整合ルール: ゲート合格なら観点を「十分」か「要対応」にし、「要対応」の観点にはその観点の修正必須または調査必須を一つ以上置く。必須項目の観点は必ず「要対応」にする。ゲート不合格なら観点をすべて「対象外」にし、観点「再利用性」の修正必須を置く。「再利用性」の対応項目はゲート不合格時だけ使う。

対応項目がある場合は「- なし」の代わりに次の形式で連番に出す。各フィールドは「- 名前: 内容」の1行で書き、フィールド内に改行や入れ子の箇条書きを入れない。

### P1: タイトル
- 種別: 修正必須 / 調査必須 / 任意改善
- 観点: 観点のいずれか / 再利用性
- 対象箇所: 短い原文引用
- 問題: 具体的な問題と読者への影響
- 改善後に満たす条件: 受入条件
- 対応方法: 最小の修正または調査経路

調査必須にはさらに「- 確認対象:」「- 必要な理由:」「- 調査先:」「- 結果ごとの対応: 支持時=>保持、非支持時=>修正・削除、結論不能時=>不要な主張は省略し、不可欠な主張は採用を保留」の4行を加える。
```

## 出力形式

依頼文の最後に置く。「この本文だけを返す。frontmatter、pass、decision、件数、前置き、後書き、schemaにない節や行は出さない。最後に確認資料の一覧などの行を足さない」と添える。

- 設計評価: [評価プロトコル](evaluation-protocol.md#設計レビュー)の設計評価本文。見出しは`# Insight設計評価: {slug}`。
- 記事評価: [評価プロトコル](evaluation-protocol.md#evaluator本文schema)の本文schema。見出しは`# Insight記事評価: {slug}`。`## 設計との照合`には設計の全D IDを並べる。

返答は`extract_agent_report.py --marker '# Insight設計評価:'`（記事は`'# Insight記事評価:'`）で取り出して保存する。
