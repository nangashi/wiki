# insightの設計・執筆への引き渡し

新規作成、実質的修正、取り込み・通常レビュー・lintで対象記事の設計がない場合にこの手順を使う。[設計schema](../design-schema.md)、[設計基準](../references/design-quality-rubric.md)、[採用基準](../references/reusability-criteria.md)を読み、レビュー開始時に[評価プロトコル](../references/evaluation-protocol.md)を読む。

## 作成

1. メインエージェントが採用・統合先、読者と用途、必要な調査を決める。調査・独立検証は既存の役割と手順で実施する。核心を置き直す、または新しい資料を根拠に加える場合は、設計の前に確かめたい主張（数値・比較対象・条件・書誌）を列挙して[外部検証](../references/evaluation-protocol.md#改善と外部検証)を行い、`evidence/<slug>.md`へ記録してからCodexに読ませる。依頼文に書いた例示の数値や言い回しも検証の対象に含め、未検証のまま設計へ渡さない。
2. 設計本文はCodex（gpt-6-astra）が書く。メインエージェントは下記の「Codexへの依頼」で起動し、出力を `designs/<slug>.md` へ保存する。既存記事から作る場合も本文をそのまま転記させず、根拠資料と照らして読者・目的・到達点・主要主張の妥当性を確認させる。比較・現実の理解・行動指針の採否はCodexに検討させ、メインエージェントが出力を確認して固定する。
3. freshな`evaluator`サブエージェントへ設計、資料、設計・採用基準を渡す。設計作成の会話・旧評価を渡さない。設計の内容と根拠、到達点自体の妥当性をレビューし保存する。
4. 必須事項をメインエージェントが分類し、必要な調査を済ませてから、Codexを新しく起動して現在の設計・必須事項・追加根拠を渡し修正させる。修正後は独立再評価する（範囲は[評価プロトコルの再評価の範囲](../references/evaluation-protocol.md#再評価の範囲)）。必須がない設計を固定して`editor`へ渡す。通常の設計確定でユーザー承認を毎回求めない。
5. editorは合格設計、根拠、記事schema・品質・日本語基準から書く。表現、見出し、段落分けは裁量とする。到達点・採用内容・根拠の強さは無断で変更しない。不備を発見したら設計へ返す。editorへの依頼では次を守る。
   - 設計から`- 適用テスト:`の行を除いた写しをスクラッチ領域に作り、それを設計として渡す。適用テストは記事にない場面への転用を確かめるためのもので、執筆担当が状況や期待する推論を知ると、その推論を本文の手順として書いてしまうため。
   - 本文に書く手順・例・判断は設計が指定したものに限り、設計の手順を別の場面へ当てはめた例や手順を足させない。
   - 外部ソース欄の書誌（著者、年、題名、誌名、巻号、頁、DOI、本文URL）は設計に書かれたものだけを使わせる。設計にない要素は補わずに省き、報告させる。書誌が欠けていれば、執筆の前に設計を直す。
   - 本文はWriteで全体を書き、旧本文を土台にする記事では書き始める前に旧本文を読ませない。
6. 記事の機械検査後、設計・執筆に参加していないfreshなevaluatorが記事単独の読解を保存し、その後に設計・資料・基準と照合する。実行・保存・完成条件は評価プロトコルに従う。

### Codexへの依頼

メインエージェントがrun-idごとに依頼文・出力・ログのパスをスクラッチ領域に用意し、依頼文には次を含める。

- 役割: insight記事の文書設計だけを書く。ファイルを作成・変更しない。最終応答は設計Markdown本文だけにし、前置き・後書きを付けない。
- 対象slug、読者と用途、採用・統合先の判断（メインエージェントが決めたもの）。
- 読むファイルのパス: `wiki/insight/design-schema.md`、`wiki/insight/references/design-quality-rubric.md`、`wiki/insight/references/reusability-criteria.md`、既存記事・既存設計（あれば）、根拠資料（調査結果はスクラッチ領域のファイルに保存して渡す）。これ以外の評価履歴を読ませない。
- 修正時は現在の設計のパスと、分類済みの必須事項・追加根拠。評価者が対応方法として示した文案は、事実（数値・比較対象・帰属）を外部検証記録か原典で確かめてから渡す（[評価プロトコル](../references/evaluation-protocol.md#改善と外部検証)）。
- 設計は簡潔にし、記事本文の想定分量より長くしないこと。主張表や「言わないこと」を網羅的に厚くせず、本文の文を書かない。
- 記事の外部ソース欄は設計の書誌だけで書かれるため、使う資料の書誌（著者、年、題名、誌名、巻号、頁、DOI、本文URL）を確認済みの値でそろえること。
- 下の「設計時には」で始まる段落の問いと注意。

```bash
codex exec -C . -s read-only -m gpt-6-astra \
  -c 'model_reasoning_effort="high"' -c project_doc_max_bytes=0 -c agents.enabled=false \
  --ephemeral -o "$design_output" - < "$design_prompt" > "$design_log" 2>&1
```

- `project_doc_max_bytes=0` でAGENTS.mdを読ませない。Codexが自分を統括役と解釈しないようにするため。
- read-onlyで起動し、書き込みはメインエージェントが行う。Codexにリポジトリの状態を変えさせない。
- 通信先は `chatgpt.com`。数分かかるため、Bashのバックグラウンド実行で起動し、完了通知を待つ。
- 終了コード0でも `$design_output` が空・設計schemaの五見出しを欠く場合は保存しない。同じ依頼文で最大2回再実行し、失敗したら未完了として報告する。メインエージェントが設計本文を代筆しない。

設計時には「読者はこの理解を得る前と後で、具体的な状況で何を変えて選ぶか」を問い、既存基準の行動指針の採否検討に使う。行動を記事の主眼にする必要はないが、説明が行動を選ぶ理由につながっているかを確認し、末尾に対策を添えるだけで済ませない。行動には、確認する情報を変える、判断を保留する、不要な介入をやめることも含む。理解・見分けを到達点とする記事に行動案を無理に足したり、根拠を超えて効果を約束したりしない。

## 修正の分類

| 修正 | 設計 | 記事 |
|---|---|---|
| 誤字、意味を変えない表現やURL移転 | 合格設計を再利用。なければ先に作成・独立レビュー | 修正・機械検査・独立最終評価 |
| 設計を本文で実現できていない | 妥当なら変更しない | 設計に沿って修正・独立再評価 |
| 読者、到達点、主要主張、比較、適用、行動、根拠や条件の変更 | 先に設計を修正・独立レビュー | 設計に依存する箇所を修正・独立再評価 |
| 設計のみの変更 | 独立再評価 | 同じ本文でも新設計との照合を含む独立再評価 |
| 設計がない記事の取り込み・通常レビュー・lint | 目的から新規設計・独立レビュー | 設計と照合し必要な修正・独立再評価 |

全文の書き直しを一律に求めない。記事の不足を消すためだけに到達点を下げない。目的変更には理由と根拠が必要で、設計レビューで確認する。統合・分割・削除・slug変更は対応設計と参照も処理し、未承認の破壊的操作は既存の確認条件に従う。

評価のみなら設計・記事を変更しない。最大3巡／同じ実質的必須問題が2回続いたら停止という改善上限は、設計と本文を往復する一連の改善にも適用し、差し戻しでリセットしない。形式・実行失敗のretryは別に扱い、未実施や失敗を合格にしない。
