# insightへの取り込み

## 条件付き参照

入力ソース・採用先・新規／追記候補を受け取る。必要な段階でのみ次を読む。

- **採用判断で読む文書**: `../schema.md` の粒度ルールと `../references/reusability-criteria.md`。`$query` はこの採用判断部分とここで指定された基準だけを読む。
- **設計時**: [設計手順](design.md)、`../design-schema.md`、`../references/design-quality-rubric.md`。新規・実質的修正は独立設計レビューを終えてから執筆する。
- **執筆時**: `../schema.md`、`../references/article-quality-rubric.md`、`../references/japanese-style-guide.md`。
- **評価時**: `../references/article-quality-rubric.md` と [評価プロトコル](../references/evaluation-protocol.md)。

核心が何を説明し、どんな推論に使えるかを明確にし、その理解と適用判断に必要な情報へ絞る。再利用性のR1〜R4で採用判定し、不合格候補と一次・二次の根拠を確保できない候補は記事化せず保留する。

## 独立調査

書籍・トピック・外部Webから新規記事を作る場合は、原則として **`finder`（Luna / medium）** に独立調査を依頼する。十分な一次資料を直接与えられ、主要主張がその資料内で追跡できる場合は作成前の独立調査を省略できるが、作成後評価は省略しない。

`finder`には入力内容、調査目的、一次資料優先、核心候補と根拠、未確認事項、URLつき出力形式を渡す。狭い検索と事実収集だけを依頼し、記事は書かせない。Astraが調査結果から設計し独立レビューを経て、別の**`editor`（Terra / medium）** が合格設計から執筆する。Astraの直接処理は[小作業の条件](../../../docs/delegation.md#小作業の直接処理)を満たす、設計引き渡しを伴わない誤字・意味を変えない局所修正に限る。採否・統合はAstraが決める。

## 書き込み手順

この手順は書込み入口 `$ingest` が使用する。`$query` で追加が承認された場合も、query自身は書き込まず `$ingest` へ引き渡してこの手順を実行する。

### ステップ1: 既存ページを把握する
`wiki/insight/index.md` を読み、すでに記録されている概念とその内容を把握する。

index.md が空の場合は以下で一覧を確認する:
```
rg --files wiki/insight/pages | sort
```

### ステップ2: 取り込む概念を列挙する
ソースから抽出した情報を「概念単位」に分解する。  
**目安**: 1つの概念 = 独立して説明できる1つのアイデア

**ソースが言語・ツール固有の場合**: ソースが特定言語（Go・Python等）・フレームワーク・ツールに特化した記事（技術ブログ・実装チュートリアル等）の場合、各概念について「この概念は言語・ツールを外しても成立するか」を確認する。成立する場合は概念を言語非依存の形で再定義してから列挙する。言語固有の実装詳細（API名・コマンド・構文）は概念そのものではなく、後工程で「具体例」として扱う。

### ステップ2.5: 各概念のコンテンツ型を分類する

各概念に以下のいずれかの型を割り当てる。型によって核心の抽出方法とステップ4の書き方が変わる。

| 型 | 判断の目安 | 核心を見つける問い |
|---|---|---|
| **原理・原則型** | 「なぜXが起きるか」を説明している | そのままWhy/Howを問う |
| **分類・タクソノミー型** | 事象をカテゴリに整理している | なぜこの分類軸が有効か。分類が前提とする原理は何か |
| **パターン・実践型** | 設計パターン・ベストプラクティスを紹介している | このパターンはどんな問題を解くか。なぜこのアプローチが有効か |
| **理論・フレームワーク型** | 他者の理論・フレームワークを要約している | 著者の問題意識・提唱動機は何か（これが核心。不明なら補足調査） |
| **ハウツー・実装型** | 手順・実装方法を説明している | 手順の背後に非自明な原理があるか（→採用判断の分岐あり） |
| **観察・事例型** | 特定の経験・実験から得た知見である | 一般化可能な原理まで引き上げられるか（→補足調査の分岐あり） |

#### 型ごとの注意点

**分類・タクソノミー型**  
分類と同時に「なぜこの分類が有効か」を抽出する。原理がなければ参照表にとどまる。定義と説明の順序は読者の理解に沿って設計する。

**パターン・実践型**  
「何ができるか（what）」より「なぜ有効か（why）」を優先して書く。パターンを生み出した「解くべき問題」が核心になることが多い。「なぜ有効か」の説明が核心の言い換えで完結していないか確認する（循環論法の禁止）。人間の心理・認知的性質に由来する場合は、その性質を名指しする（例：認知的不協和、損失回避、自動化）。機序が未確定でも条件付きの関係や介入効果で推論できる場合は採用できる。説明や利用判断を変える不足だけを調査する。

**理論・フレームワーク型**  
著者の提唱動機がソースに明示されていない場合は補足検索を行い、動機を特定してから書く。動機が不明のまま書いたページは本質が推測補完になるリスクがある。

**ハウツー・実装型（採用判断の分岐）**  
```
手順の背後に非自明な原理がある？
  YES → 原理を核心として書く。手順は原理を体現する具体例として位置づける
  NO  → 採用しない候補として扱う（下記の提案フォーマットでユーザーに確認）
```

提案フォーマット:
```
「<概念名>」はハウツー型のコンテンツですが、一般化可能な原理が見当たりません。
採用しない場合は技術メモとしてコード・設定コメントに残すことを推奨します。
採用しますか？
```

**観察・事例型**  
特定の経験から一般化可能な原理（「この状況では常にXが起きる、なぜなら…」）まで引き上げられるか確認する。引き上げられない場合は補足調査を提案する。一般化できない観察は事例ページとしてではなく、関連する原理ページへの追記として吸収することを検討する。

**原理・原則型（認知バイアス・ヒューリスティック・心理メカニズムを扱う場合）**  
比較・現実の理解・行動指針を設計で検討し、採否と理由を記す。認知系の分類だけで対処を一律に追加しない。採る場合はいつ何をするかと根拠の範囲を示す。

### ステップ3: 各概念について新規 or 追記を判断する
schema.mdの「粒度ルール > 新規 vs 追記の判断フロー」に従う。

### ステップ4: 設計してから書く・更新する

新規作成・実質的修正・対象記事の設計がない場合は[設計手順](design.md)を実行し、独立レビュー済みの設計を先に固定する。設計がない既存記事の作成・変更の分類・設計への差し戻しは同手順を正本とする。

別の執筆担当へ合格設計と根拠、記事schema・品質・日本語基準を渡す。概要は何の概念で現実の何に関わるかを示し、説明関係を読める順序で書く。比較・適用・行動を研究紹介の付録にせず、設計の到達点を実現する。見出し・段落数や核心の一文を固定しない。

新規記事は `pages/<slug>.md` にschemaのfrontmatterと本文形式で作る。実質的修正ではupdatedを今日の日付に更新し、必要な本文・関連・出典を一緒に確定する。出典IDは振り直さない。設計の不備や根拠不足が判明したら未確認の内容を補わず設計へ戻す。

#### 草稿・改稿後の確認

新規・追記とも、執筆担当が次を確認してから草稿を確定する。改善ループで改稿した場合も、変更箇所と影響する節を確認する。

- 各節が読者のどの問いに答えるかを確認する。同じ問いに同じ内容で答えている箇所は、まとめるか、それぞれの役割が異なる説明に直す。概要の要約や、条件を説明するために必要な再提示は残す。節数や文字数の削減を目標にせず、読み進めると理解や判断材料が増える構成にする。
- 改稿した箇所は前後を照合し、適用条件、因果の向き、断定の強さ、数値の単位・起算点・回数の数え方が意図せず変わっていないか確認する。例えば「初回を含めて3回」と「3回再試行」は区別する。統合・削除した場合は、判断に必要な条件分岐が残っているかも確認する。元の主張に誤りが見つかった場合は根拠に基づいて修正し、具体化のために未確認の原因や結果を補わない。

問いを公開本文の見出しにしたり、確認メモを保存したりする義務は設けない。この確認後も、ステップ5の最終稿の独立評価を実行する。

草稿を確定したら `bash wiki/insight/tools/textlint-check.sh <記事パス>` を実行する。必須修正は解消し、要判断・参考指摘は記事全文と日本語基準に照らして採否を決める。修正後に再実行し、残した指摘の理由を報告する。新規記事は `python3 wiki/insight/tools/insight_source_validator.py <記事パス>` の診断をすべて解消するまで正式保存・新規公開しない。

### ステップ4.5: 関連リンクを張る

- 新規・更新ページの「関連」セクションに、理解や判断に役立つ関連概念へのリンクを追加
- 相互リンクは必須にしない。関連先からも独自の説明が必要な場合だけ、そのページを更新する
- リンク形式: `[[スラグ]]` + 関係の説明
- 共通スキルが取得した被リンクを参考にする

本文、`## 関連`、`## 外部ソース`をこの時点で確定し、変更されたinsightページをすべて評価対象へ加える。被リンクの取得だけでは記事を変更せず、再評価も発生しない。

### ステップ5: 記事品質の評価・改善

新規記事と本文を変更した全記事に [評価プロトコル](../references/evaluation-protocol.md) を実行する。freshな独立評価、検証・保存、必須調査、最小改善、新しい独立再評価、停止条件を省略しない。最終評価後は記事・設計blobを変更しない。

### ステップ6: 共通スキルへ引き渡す

全対象記事で、最終評価が保存され、記事・設計hashと合格設計評価参照が現内容に一致してから共通スキルへ引き渡す。設計不足・設計評価未実施は未完了として報告する。新規ページは現行rubric、記事hash一致、採用適合、必須項目なし、出典形式の公開条件を満たすまで保留とする。index更新と被リンク取得は共通スキルが実行する。

### ステップ7: 作業サマリを出力する
以下を報告する:
- 新規作成したページ一覧（タイトル・スラグ）
- 更新したページ一覧（タイトル・追加内容の要約）
- スキップした概念（理由付き）
- 追加した関連リンク
- 初回／最終の公開判断、修正必須・調査必須の解消内容、任意改善と保持した良い点
- Astraとeditorが行った改善と、停止時に残った課題
- 外部検証を行った主張と、未確認のまま残した主張
- 変更記事と根拠の場所、公開／保留、残課題・停止理由
