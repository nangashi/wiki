# Insight Wiki スキーマ

このファイルは insight コレクションの形式と共通書き込み手順を定義する。コレクション構成と振り分けは `wiki/collections.md`、insightへの採用判定は `wiki/insight/references/reusability-criteria.md`、記事品質は `wiki/insight/references/article-quality-rubric.md`、日本語は `wiki/insight/references/japanese-style-guide.md`、評価・改善の実行方法は `wiki/insight/references/evaluation-protocol.md` を正本とする。

---

## ディレクトリ構成

```
wiki/
  collections.md     # コレクション定義（全スキル共通）
  insight/
    schema.md        # このファイル（ルール定義）
    pages/           # wikiページ（1概念1ページ）
      <slug>.md
    references/      # 採用・品質基準と共通評価プロトコル
      <name>.md
  it/
    schema.md        # ITコレクションのルール定義
    pages/           # ITコレクションのページ
```

## ページフォーマット

### frontmatter

```yaml
---
title: "概念名（日本語）"
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
---
```

評価は `evaluations/insight/<slug>/` の評価ファイルにある `rubric_version` と `target_blob` で追跡する。評価結果を記事frontmatterへ保存しない。

### 本文構成

```markdown
# 概念名

## 概要
1〜3文で概念の核心を説明する。

## 詳細
詳しい説明、背景、仕組み、使い方など。

## 関連
- [[関連概念スラグ]] — この概念との関係を1行で説明
- [[別の概念スラグ]] — この概念との関係を1行で説明

## 外部ソース
- S1（一次）: https://example.com/original — 記事の核心となる経験的主張を支える。本文では該当主張の末尾から[S1]で参照する。
```

- `## 概要`はindexサマリの生成元とする。他の説明セクションは必要なものだけ使う（例：「詳細」不要なら省略）
- 追加セクション（例：「具体例」「注意点」「歴史」）は内容に応じて自由に追加してよい
- `## 外部ソース`は必須かつ記事末尾に1つ置く

### 本文中のリンク記法

本文（詳細セクションなど）の流し文章中でリンクを張る場合は、`概念名（[[slug]]）` の形式を使う。

```markdown
# NG: エイリアス記法（[[slug|表示テキスト]]）は使わない
生産性の[[proxy-metrics-knowledge-work|代理指標]]になる。

# OK: 日本語を先に書き、括弧内にリンクを置く
生産性の代理指標（[[proxy-metrics-knowledge-work]]）になる。
```

- 概念名がすでに括弧付き表記を含む場合（例: `制約理論（TOC）`）は `制約理論（TOC・[[theory-of-constraints]]）` のように区切り文字を使う
- 関連セクションでは `[[slug]]` のみで十分（タイトルは説明文で補う）

## 命名規則

- **ファイル名**: 英語またはローマ字表記の kebab-case（例: `transformer-architecture.md`, `attention-kikou.md`）
- **タイトル**: 日本語（frontmatter の `title` フィールドおよび本文 `# 見出し`）
- **スラグ**: ファイル名から `.md` を除いたもの（例: `transformer-architecture`）

## 粒度ルール

### 1概念1ページの原則
- **1ページ = 単一のアイデア・技術・用語・手法・人物、または複数概念の間の関係・対比・パターン（関係概念）**
- ページを読んで「これは複数のことを説明している」と感じたら分割候補
- ページが2〜3行しかなく独立性が低ければ、関連ページへの追記候補

**関係概念の例（通常の概念ページと同じフォーマットで作成する）:**
- XとYの定義アプローチの対比
- 複数研究にまたがる評価パラダイムの分類
- 同一問題に対する複数手法のトレードオフ比較
- ※ 関係概念ページは末尾の`## 外部ソース`に複数項目が並ぶことが多い

### 新規 vs 追記の判断フロー
```
抽出した情報 → 同名または非常に類似した既存ページがある？
  YES → そのページに情報が不足している？
    YES → 既存ページに追記
    NO  → 既に記録済み、スキップ
  NO  → 独立した概念として成立する？
    YES → 新規ページを作成
    NO  → 最も関連するページに追記
```

### 既存ページとの類似性チェック
- 完全同一概念: 同じページに追記（重複ページを作らない）
- 上位概念: 子概念ページを新規作成し、理解に必要な方向へ関連リンクを張る
- 類似だが別概念: それぞれ別ページとして作成し、区別に役立つ関連リンクを張る

## 外部ソース記録ルール

frontmatterに`source`または`sources`を置かない。記事末尾の`## 外部ソース`へ、次の形式で1ソース1項目を記録する。

```markdown
- S1（一次）: <URLまたは書誌情報> — <何を支えるか>
- S2（二次）: <URLまたは書誌情報> — <何を支えるか>
- S3（参考）: <URLまたは書誌情報> — <補足として何に使ったか>
```

- IDは`S`と正の整数で表し、記事内で重複させない。欠番や項目の並べ替えで振り直さない。ソースを削除するときは、そのIDを参照する主張の根拠も見直す
- 一次は原典・原論文・公式資料・著者本人、二次は信頼できる解説・レビュー、参考は核心の根拠に使わない補足とする。分類は実際に内容を確認してから付ける
- 数値、実験結果、研究名、メタ分析、特定介入の効果、核心を支える経験的主張は、主張直後に`[S1]`、複数なら`[S1][S2]`と記す。通常の説明文すべてへIDを付けない
- 各項目の説明は、対応する主張または支える範囲を特定する。「参考にした」だけでは不十分。文数や終止符の形式は指定しない
- `topic:`は調査指示であって根拠ではないため、外部ソースに記録しない
- 調査中だけ`- S1（要確認）: <URLまたは書誌情報> — 対応する主張を未確認。`を許容する。新規記事は要確認を解消し、一次または二次を1つ以上確保するまで正式保存・index追加しない
- 既存記事で外部ソースが未確認なら`外部ソース未確認。`とする。これは移行状態の恒久的な別形式ではなく、`review-page`/`lint`で解消すべき品質問題である

## 共通書き込み手順

この手順は書込み入口 `$ingest` が使用する。`$query` で追加が承認された場合も、query自身は書き込まず `$ingest` へ引き渡してこの手順を実行する。

### ステップ1: 既存ページを把握する
`wiki/insight/index.md` を読み、すでに記録されている概念とその内容を把握する。

index.md が空の場合は以下で一覧を確認する:
```
find wiki/insight/pages -name "*.md" | sort
```

### ステップ2: 取り込む概念を列挙する
ソースから抽出した情報を「概念単位」に分解する。  
**目安**: 1つの概念 = 独立して説明できる1つのアイデア

**ソースが言語・ツール固有の場合**: ソースが特定言語（Go・Python等）・フレームワーク・ツールに特化した記事（技術ブログ・実装チュートリアル等）の場合、各概念について「この概念は言語・ツールを外しても成立するか」を確認する。成立する場合は概念を言語非依存の形で再定義してから列挙する。言語固有の実装詳細（API名・コマンド・構文）は概念そのものではなく、後工程で「具体例」として扱う。

### ステップ2.5: 各概念のコンテンツ型を分類する

各概念に以下のいずれかの型を割り当てる。型によって核心の抽出方法とステップ4の書き方が変わる。

| 型 | 判断の目安 | 核心を見つける問い |
|---|---|---|
| **原理・原則型** | 「なぜXが起きるか」を説明している | そのままWhy/Howを問う |
| **分類・タクソノミー型** | 事象をカテゴリに整理している | なぜこの分類軸が有効か。分類が前提とする原理は何か |
| **パターン・実践型** | 設計パターン・ベストプラクティスを紹介している | このパターンはどんな問題を解くか。なぜこのアプローチが有効か |
| **理論・フレームワーク型** | 他者の理論・フレームワークを要約している | 著者の問題意識・提唱動機は何か（これが核心。不明なら補足調査） |
| **ハウツー・実装型** | 手順・実装方法を説明している | 手順の背後に非自明な原理があるか（→採用判断の分岐あり） |
| **観察・事例型** | 特定の経験・実験から得た知見である | 一般化可能な原理まで引き上げられるか（→補足調査の分岐あり） |

#### 型ごとの注意点

**分類・タクソノミー型**  
分類と同時に「なぜこの分類が有効か」を必ず抽出する。原理がなければ参照表にとどまる。概要には分類の定義より先に「この分類を成立させる原理」を書く。

**パターン・実践型**  
「何ができるか（what）」より「なぜ有効か（why）」を優先して書く。パターンを生み出した「解くべき問題」が核心になることが多い。「なぜ有効か」の説明が核心の言い換えで完結していないか確認する（循環論法の禁止）。人間の心理・認知的性質に由来する場合は、その性質を名指しする（例：認知的不協和、損失回避、自動化）。独立したメカニズムを特定できない場合は補足調査を提案する。

**理論・フレームワーク型**  
著者の提唱動機がソースに明示されていない場合は補足検索を行い、動機を特定してから書く。動機が不明のまま書いたページは本質が推測補完になるリスクがある。

**ハウツー・実装型（採用判断の分岐）**  
```
手順の背後に非自明な原理がある？
  YES → 原理を核心として書く。手順は原理を体現する具体例として位置づける
  NO  → 採用しない候補として扱う（下記の提案フォーマットでユーザーに確認）
```

提案フォーマット:
```
「<概念名>」はハウツー型のコンテンツですが、一般化可能な原理が見当たりません。
採用しない場合は技術メモとしてコード・設定コメントに残すことを推奨します。
採用しますか？
```

**観察・事例型**  
特定の経験から一般化可能な原理（「この状況では常にXが起きる、なぜなら…」）まで引き上げられるか確認する。引き上げられない場合は補足調査を提案する。一般化できない観察は事例ページとしてではなく、関連する原理ページへの追記として吸収することを検討する。

**原理・原則型（認知バイアス・ヒューリスティック・心理メカニズムを扱う場合）**  
人間の認知・行動に作用する原理（バイアス・ヒューリスティック・心理効果など）を扱うページは「どう対処・補正するか」を必ず含む。セクションを分けるかどうかは問わない（詳細に組み込んでもよい）。この型の概念は「意思決定・行動への影響」と「その補正方法」がセットで実用的核心になるため、対処が書かれていないページは本質の半分しか捉えていない。

### ステップ3: 各概念について新規 or 追記を判断する
上記「粒度ルール > 新規 vs 追記の判断フロー」に従う。

### ステップ4: ページを書く・更新する

**新規ページの場合:**
- ファイル名: 命名規則に従い `wiki/insight/pages/<slug>.md` として作成
- frontmatter: title・created・updated を記入（`sources`は禁止）
- 本文: 概要 → 詳細 → 関連 → 外部ソース の順で記述
- **概要**: ステップ2.5 で特定した型の「核心を見つける問い」に対する答えを1文で書いてから、説明・背景に続ける（分類や手順の定義を先置きしない）。核心文は一読で理解できる簡潔な1文にする（目安: 読点2〜3個・80字以内）。すべての因果・条件を1文に詰め込まず、圧縮で失われるニュアンスは直後の1〜2文で平易に補う。概念名・概要の中で非自明な用語を使う場合、その用語を概要の直後または詳細の冒頭で定義してから説明に入る（例：「フレーミング効果」を説明するなら「フレーム＝参照点の設定」を先に定義する）
- **詳細**: 概念の普遍的な構造・原理・メカニズムを書く場所。核心との接続は各段落の説明の流れに織り込み、「これは核心の○○から必然的に導かれる」という定型文を段落ごとに繰り返さない。特定言語・ツール固有の実装（コード・コマンド・API名）はデフォルトで「具体例」セクションへ分離し、最小限の1例にとどめる。詳細セクションを読んで「これはGoの話だ」「これはPostgreSQLだけの話だ」と感じたら、言語・ツールを外して書き直す。
- **適用トリガー**: 型を問わず、「読者がどんな状況に遭遇したらこのページを思い出すべきか」を1行以上書く。独立セクションでも、対処・詳細セクションへの組み込みでもよい。核心から自明に導けず推測になる場合は無理に書かない。

**追記の場合:**
- 既存ページの `updated` を今日の日付に更新
- 新しい情報を適切なセクションに追記
- 末尾の`## 外部ソース`へ確認済みソースを追加し、対象となる強い主張へsource IDを付ける（重複しない場合）

### ステップ4.5: 関連リンクを張る

- 新規・更新ページの「関連」セクションに、理解や判断に役立つ関連概念へのリンクを追加
- 相互リンクは必須にしない。関連先からも独自の説明が必要な場合だけ、そのページを更新する
- リンク形式: `[[スラグ]]` + 関係の説明
- 被リンクは `python3 .agents/skills/lint/wiki_structure.py backlinks insight:<slug>` で取得する

本文、`## 関連`、`## 外部ソース`をこの時点で確定し、変更されたinsightページをすべて評価対象へ加える。被リンクの取得だけでは記事を変更せず、再評価も発生しない。

### ステップ5: 記事品質の評価・改善

新規作成したページ、および本文を変更したページは変更の大小にかかわらず `evaluation-protocol.md` を実行する。評価履歴の `target_blob` と現在の記事内容を常に一致させる。

1. 新しい履歴なしのevaluator（Sol）が `article-quality-rubric.md` と `japanese-style-guide.md` で評価する。AstraがCodex標準のサブエージェント機能で起動し、前回評価や執筆会話を渡さず、記事を変更させない。起動と検証の詳細は `evaluation-protocol.md` に従う。
2. 調査必須項目は、同プロトコルに従い別のevaluatorで検証し、結果に応じて維持・修正・削除を決める。未確認を誤りと断定せず、必要な理由と結果ごとの対応を明示する。核心に不要な主張なら削除で解消してもよい。
3. 修正必須・調査必須が残る場合、Astraが依存順に1〜3項目を選び、必要な調査後にeditor（Terra）へ改善を委譲する。任意改善は原則対応せず、公開・終了を妨げない。Astraとeditorは独立評価を代行しない。
4. 改善後は、前回評価結果を渡さない新しい履歴なしのevaluatorで再評価する。
5. 必須項目が解消されるか停止条件に達するまで最大3回とし、評価履歴を `evaluations/insight/<slug>/` に保存する。

具体例・数値・コード・固有名の不在だけを低品質とみなさない。未知ケースへの推論力、論理的な接続、適用境界、事実基盤、情報設計、日本語の自然さを共通ルーブリックで判断する。

最終評価を保存した後は対象ページのblobを変更しない。変更が必要になった場合は、その変更を適用してから新しい評価を実行し直す。

### ステップ6: index.mdを生成する

全変更ページの最終評価が保存され、`target_blob`が現内容と一致してからindexを最後に生成する。新規ページが停止条件までに公開条件を満たさなければindexへ追加しない。

```bash
python3 .agents/skills/lint/wiki_structure.py index --collection insight
# 新規記事の公開時。現行rubric・記事hash一致・採用適合・必須項目なし・出典形式をスクリプトで確認する
python3 .agents/skills/lint/wiki_structure.py index --add insight:<slug>
```

サマリは`## 概要`の最初の段落を改行だけ折り畳んで使う。別途執筆・短縮せず、内容の改善は記事の概要で行う。既存カテゴリと公開済み項目は保持され、新規項目は「未分類」に入る。必要なら項目の分類先だけ移動する。未公開の草稿は`--add`なしでは追加されない。

### ステップ7: 作業サマリを出力する
以下を報告する:
- 新規作成したページ一覧（タイトル・スラグ）
- 更新したページ一覧（タイトル・追加内容の要約）
- スキップした概念（理由付き）
- 追加した関連リンク
- 初回／最終の公開判断、修正必須・調査必須の解消内容、任意改善と保持した良い点
- Astraとeditorが行った改善と、停止時に残った課題
- 外部検証を行った主張と、未確認のまま残した主張
